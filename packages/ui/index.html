What you are looking at

The demonstrator opens paused at T+00:00 with a short walkthrough. Press ? in the Control panel to replay it. There are three views of the same running simulation, chosen with the switch in the Control panel. Switching views never changes what the simulation does.

  • Artefacts (the default): the orchestrator's dependency graph. It shows the three triggers, the assets they materialise (forecast, features, announcement) and each shim calling one of our modules. It also shows the messages that feed the orchestrator and carry its output to consumers.
  • Logical: the whole information flow, in three regions. World is the ocean and the ship's sensors. System holds ingestion, the orchestrator, the stores and pygeoapi. Onboard consumers are the systems that use the forecast. The broker sits on the System–Consumers boundary.
  • Physical: the same traffic laid over a candidate shipboard deployment, with network zones, nodes and firewall gates.

Tokens are the small lettered documents moving along the lines. Each one is a real call, write, read or message in the simulation, lettered by the standard it follows (S SensorThings, E EDR, C CoverageJSON, M MQTT and so on; the key is at the foot of the consumers column). Hover a token to see what it carries. Pause, then click it to see a mock payload. Countdowns show what will happen next: the drift sensor's next check, when the forecast goes stale, and retry timers. Click a store to see its rows.

Why an asset-driven pipeline

The orchestrator does not run a fixed job on a timer. It keeps a graph of data assets (observations, climatology, the previous forecast, forecast, features, announcement) and rebuilds what is out of date when something gives it a reason. There are three reasons, or triggers:

  • Drift: every 10 s the drift monitor compares recent observations with the current forecast. If enough inputs disagree for long enough, it requests a run.
  • Staleness: a forecast older than 180 s is replaced on schedule, even if nothing has drifted.
  • Manual: the watchkeeper asks for a run through the run-request API.

Only one run happens at a time. A request that arrives during a run waits in a queue. Later requests merge into the queued one, and the log records every cause (for example drift + manual). So a burst of triggers costs one extra run, not many. Each asset records when it was last built, so it is always clear how fresh the forecast is and why it was rebuilt.

Build vs adopt

We build only the parts that make the system worth having. Commodity parts are adopted from open source. The screen uses one visual language for this:

  • Solid outline, pale steel fill: ours. Ingestion, drift monitor, model runner, feature detector, announcer, run-request API, and the shims.
  • Dashed outline: off-the-shelf. The orchestrator (Dagster), the brokers (Mosquitto) and the geospatial API (pygeoapi).
  • Double outline: our data in an adopted store. Observations DB (Postgres), NetCDF store, Features DB (PostGIS).

Each of our modules sits inside the asset it computes. The orchestrator reaches it only through a one-line shim, and the modules import nothing from the orchestrator. The build checks this boundary and fails if it is broken. That is what keeps the orchestrator replaceable.

Caveats. In the demonstrator every element is custom simulation code; the styling only shows the production decision. Of our modules, the model runner is the real special sauce. Ingestion QC and drift scoring are mostly standard techniques with our own thresholds. In production the shims will grow some integration glue (request merging, capped retries), and that glue needs an owner.

Robustness

  • Retries with backoff. Take the model runner or feature detector offline (the pause button before its title). Its shim turns amber and retries after 2, 4, 8, then every 10 s. Nothing half-finished is committed. Bring it back and the next retry completes the run. Retry belongs to the orchestrator, so the countdown is on the shim, not in our code.
  • Atomic commits. A forecast is staged and then committed in one step, with a digest. A failed run leaves the previous forecast in place.
  • Nothing lost in an outage. Stop ingestion or the Observations DB and readings queue in the sensor broker. Start it again and the backlog drains in order, with every reading stored once.
  • Consumers verify. Each consumer fetches what was announced and checks the digest or feature count, showing ✓ or ✗.
  • Late joiners catch up. A consumer added mid-run reads the broker's retained latest announcement and fetches the current forecast at once.
  • Bad data is rejected. Ingestion rejects non-numbers, out-of-range values and sudden jumps, and logs the reason.
  • Repeatable. The same seed and the same actions always give the same event log, so a demo can be rehearsed and a fault reproduced.

Demo simplification: retries here never give up. Production would cap them, raise an alert and let the staleness schedule recover.

Production architecture

The physical view shows a candidate deployment on the ship that works with the shore link down. It has four zones, left to right:

  • Instrument network (OT): DAQ gateways, sensor broker and ingestion. It accepts no inbound traffic from mission systems.
  • Processing enclave: the orchestration node (Dagster, shims and our in-process modules), a compute node for the model runner, a data node for the three stores, and an ops node for shore transfer.
  • Distribution zone: pygeoapi, the broker and the run-request API, the only things consumers can reach.
  • Mission network: the watchkeeper's workstation and the onboard consumers.

Tokens follow real network links and light a firewall gate wherever they cross a zone. The shore link is up for part of each cycle: new climatology arrives only when it is up, and export bundles wait in an outbox when it is down. Parts with no simulated behaviour (observability, backup, registry) are greyed out.

The module boundary is an import boundary, not a process boundary. Only the model runner gets its own process (via Dagster Pipes). The 10 s drift check is demo time-compression; production would check every 30 s or more.

Scenarios to try

  1. Drift. In Ocean, shift two or more inputs. Watch the drift chart move away from the forecast until drift is declared. A new forecast is built, features are detected, the forecast is announced and every consumer shows ✓.
  2. Staleness. Change nothing. When the staleness countdown reaches 0:00, a scheduled run replaces the forecast.
  3. Queue and merge. Press Request a run on the Watchkeeper card during a run, then press it again. The two requests become one queued run, and the log shows both causes.
  4. Module offline. Pause the model runner (on forecast) during a run. Watch the amber retries, then resume it.
  5. Outage. Stop ingestion for 30 s. The sensor broker's queue grows, then drains when you start it again.
  6. Noisy sensor. Raise a sensor's noise to 3σ. Open the event log to see the rejected spikes and their reasons.
  7. Late joiner. After the first announcement, press + Consumer. The new consumer catches up at once.
  8. Capabilities. Switch the power off, add the wave-height sensor and future forecasts, and switch on again. Watch the consumers tailor themselves to the catalogue during the handshake.

Controls are coloured by who would really have them: teal for the sea and sensors, violet for the ship's operator, and the Control panel for the presenter. Use the ½×–60× speeds to skip waits, and Step to move one second at a time. Guided tours that play these scenarios without a presenter are planned.
